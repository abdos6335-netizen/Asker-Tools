# Clash management and engineering approval workflow

## Clash Manager (0.1.0)
Provides an in-memory review/tracking layer for exact clash records: stable clash ID, owner, status, due date, notes, and severity classification. Current severity mapping is intentionally conservative and provisional (mesh interference HIGH; clearance violation MEDIUM; other states INFORMATION) and is not a project risk standard. Selecting a clash selects its two scene nodes; it does not isolate or modify them. The initial rollout exposes exact-mesh scanning, severity counts, a clash list with discipline/name context, node selection, translation/rotation alternative generation and proposal ranking, plus session-level owner/status/due-date/note editing. The user must configure the project's required check-type identifiers (semicolon-separated in the rollout) and jurisdiction before simulation; the engine does not invent a default checklist or jurisdiction. Generated alternatives remain unvalidated until a selected candidate is simulated against those explicit project-required check types. The UI then exposes a separate named approval action and a further explicit apply action; an unapproved or stale-scene candidate cannot be applied. Tracking and project rule/mapping state can be persisted through the XML project store.

## Governance and transaction layer (0.1.0)
Approval requires a candidate already marked simulation-validated, a successful exact simulation, no introduced clashes, no missing rules, no critical violations, a named approver, date, and reason. Applying is a separate explicit call and supports the approved translation or pivot rotation action on the candidate's affected node. Rotation is accepted only around the object's captured world pivot. Before simulation, the engine re-inspects the discipline inventory and exact triangle snapshots and compares node IDs, classification, envelope metadata, bounds, objectTransform, pivot and triangle coordinates with the scan snapshot. Any change requires a fresh scan. At apply time, objectTransform (including parent and object-offset effects) and world pivot must still match the simulation snapshot; stale scene state blocks application. Rollback restores the original transform only if the node still matches the transform produced by that transaction, preventing rollback from overwriting later edits. Duplicate transaction IDs are rejected. Audit events are retained in memory and can be saved to the project XML file. Active approvals and transactions are intentionally not restored on project load. Each approval is single-use; after an apply attempt, a new scan/simulation/approval is required before another apply.

APIs:
- `AT_ClashManager.load clashes`, `counts`, `selectClash index`, `setTracking clashId owner:<string> status:<string> dueDate:<string> note:<string>`
- `AT_CoordinationGovernance.approve candidate simulation approver reason approvalDate`
- `AT_CoordinationGovernance.applyTranslation proposalId nodeRef offset transactionId` or `applyRotation proposalId nodeRef axis angleDegrees pivot transactionId`
- `AT_CoordinationGovernance.rollback transactionId reason`

## Safety limits
Project XML persistence is available for rules, mappings, element envelope metadata, tracking, integration revision tokens and audit history. User identity authentication, role-based approval signatures, concurrency control, full scene snapshots, linked-document revision locking, and multi-node atomic transactions are not implemented. Apply supports translation and pivot rotation only and must not be used as an unattended engineering decision. A real project deployment requires in-host QA and explicit engineering review.


The Clash Manager includes severity/discipline filters, text search, selection of both clash elements, and owner/status/due-date tracking. Filtering is presentation-only and does not change the underlying clash set or scan snapshot.
